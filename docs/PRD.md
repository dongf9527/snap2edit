## 1. 背景与问题

### 1.1 背景

将静态图片（信息图 / 方法论图 / 流程图 / 对比图）还原为可编辑文件，是咨询顾问、
方案工程师、内容创作者的高频工作。团队此前以"六步标准流程"（原图分析 → HTML+SVG
生成 → 截图比对收敛 → PPTX 原生生成 → 渲染校验 → 终检）完成了多张复杂信息图的
高保真复刻，沉淀了组件库、坐标换算公式、字体处理经验和十余个校验脚本，
验证了方法学的可复现性（详见 `docs/WORKFLOW.md`）。

但整个流程以一次性脚本 + 人工执行的方式运行，无法沉淀为可持续复用的资产。

### 1.2 问题定义

| 编号 | 痛点 | 影响 |
|---|---|---|
| P1 | **双产物靠人肉同步**：同一份布局要分别为 SVG 和 python-pptx 各写一遍，任何修改需两处同步 | 改一处漏一处，两版内容漂移 |
| P2 | **校验靠肉眼**：文案覆盖、无位图、无嵌入图片、文本溢出等硬约束全靠人工盯 | 漏检风险高，验收标准不稳定 |
| P3 | **经验难沉淀**：坐标换算公式、中文字体 a:ea 双保险、关继承阴影、字宽实测等经验散落在注释和人脑里 | 新人上手慢，老坑重踩 |
| P4 | **无法规模化**：没有脚手架与组件库，每张图从零开始 | 单张图复刻成本高，无法批量 |

### 1.3 机会

流程已验证、脚本已存在，缺的只是**工程化封装**：把"两遍手写"收敛为"一份规格、双产线渲染"，
把"肉眼校验"固化为"自动校验门"，把"经验"编码为"默认行为"。

## 2. 产品定位与目标

### 2.1 一句话定位

> Snap2Edit 是一个规格书驱动的截图复刻引擎：输入一份布局规格（YAML），
> 同步产出全可编辑的 HTML+SVG 与原生 PPTX，并自动执行全部质量校验。

### 2.2 产品目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 一份规格，双产物同源同步 | HTML 与 PPTX 由同一 spec 渲染，文案 100% 同源 |
| G2 | 硬约束自动校验 | 四道校验门全绿才允许交付；报告可存档 |
| G3 | 经验固化为默认行为 | 换算公式、CJK 字体、关阴影、字宽实测内置于引擎 |
| G4 | 五分钟上手 | `new → 编辑 spec → build → check` 四步完成首个产物 |

### 2.3 非目标（v1 明确不做）

- ❌ 端到端像素级自动矢量化（任意位图直接转 SVG 轮廓）——可靠性差，非本产品路径；
- ❌ 全自动"看图出规格"（v2 以 AI 辅助形式引入，见 F8）；
- ❌ PPT 动画、模板美化、母版管理；
- ❌ 挑战 Canva/Figma 类设计工具——只做"还原与可编辑化"这一件事。

## 3. 目标用户与核心场景

### 3.1 用户画像

| 画像 | 描述 | 关键诉求 |
|---|---|---|
| U1 咨询/方案工程师 | 需要把参考图改成自有方案图，交付 PPT | 快、像、可编辑、不侵权（重绘而非抠图） |
| U2 内容创作者 | 公众号/课程配图需要 HTML 版与 PPT 版并存 | 一份内容两个格式，改字不用改两遍 |
| U3 开发者/AI 工作流搭建者 | 把复刻能力嵌进自动化流水线（含 LLM Agent） | 结构化输入、可编程、校验可断言 |

### 3.2 核心用户旅程（U1）

1. 拿到一张参考图，用 `snap2edit new` 建项目；
2. 对照原图编写 `spec.yaml`（或让 AI 起草后人工核对 N1 结点）；
3. `snap2edit build` 一键得到 HTML 与 PPTX；
4. `snap2edit check --original 原图.png` 得到校验报告，按报告修 spec；
5. 报告全绿 → 交付两份文件，源文件进 Git。

## 4. 术语表

| 术语 | 定义 |
|---|---|
| 规格书（spec） | 描述画布、字体、色板、文案清单与带 id 元素列表的 YAML 文件，双产线唯一事实源 |
| 产线① / 产线② | spec → HTML+SVG；spec → 原生 PPTX 两条渲染管线 |
| 原生形状 | PowerPoint 中的矩形/文本框/连接线等对象，可独立选中编辑；与"嵌入图片"相对 |
| 校验门 | 自动化的质量断言组：门1 HTML、门2 PPTX、门3 边界、门4 截图 |
| 结点 N1–N6 | 六步标准流程中的里程碑（规格书/HTML/PPTX/两次校验/终检），见 WORKFLOW.md |

## 5. 功能需求

优先级：P0 = v0.1 必须；P1 = v0.5；P2 = v1.0+ / v2.0。

### F1 规格书 schema 与校验（P0，已实现）

- YAML 格式；含 `project / canvas / slide / font / palette / texts / elements`；
- 元素类型 v0：`rect / rrect / pill / text / line / arrow`；
- 加载即校验：类型合法、几何字段齐全、id 唯一、携带文字必有 size、占位符黑名单（XXX/TODO/待补充/【/undefined/NaN）；
- **验收**：非法 spec 在 build 前即报错且错误信息含元素定位（`elements[i](id)`）。

### F2 产线①：HTML+SVG 渲染（P0，已实现）

- 全部文字为真实 `<text>`；每个元素带 id 的独立最小单元；**禁止 `<image>`/`data:image`**；
- 箭头渲染为线段 + 三角两个独立单元；
- viewBox 与画布 1:1；HTML 壳提供 `#stage`/`#canvas` 锚点供截图与二次开发；
- **验收**：对 demo spec，门1 四项断言全过。

### F3 产线②：原生 PPTX 渲染（P0，已实现）

- 100% 文本框 + 形状（`Picture = 0`）；形状 name = 元素 id，可单独寻址；
- 内置规则：px→EMU、px→pt 换算；文本框 margin=0、word_wrap=False；`a:ea`/`a:cs` CJK 字体双保险；关闭继承阴影；箭头=连接线+tailEnd 三角；
- **验收**：对 demo spec，门2 四项断言全过；PowerPoint/WPS 可打开且全部元素可编辑。

### F4 校验门（P0，已实现）

| 门 | 检查项 |
|---|---|
| 门1 HTML | `<text>` 数量覆盖、无位图、文案清单逐条在场、占位符黑名单 |
| 门2 PPTX | 幻灯片尺寸 EMU、Picture=0、文案清单逐条在场、占位符黑名单 |
| 门3 边界 | PIL 实测每段文字宽度 vs 可用宽度（w 或画布右缘），溢出即失败 |
| 门4 截图 | Playwright 元素级截图、非白像素 >2%、可选 `--original` 启用 16px 块差异（总平均差异 <10/255 达标） |

- **验收**：`check` 输出 `build/report.md`，任一项失败退出码非 0（CI 可断言）。

### F5 CLI（P0，已实现 / P1 部分）

- `new <dir>`：生成 spec 模板（P0）；
- `build <dir>`：双渲染到 `<dir>/build/`（P0）；
- `check <dir> [--original IMG] [--no-shot]`：四道门 + 报告（P0）；
- `loop <dir> [--max-iters N]`：build+check 自动迭代直至收敛（P1）。

### F6 组件库扩充（P1）

- 在 v0 六种元素上新增：`cube`（立方体）、`matrix-cell`（矩阵格子）、`flow-box`（流程框）、`icon`（图标库：brain/chart/network/sparkle 等，移植自历史 svg_lib）；
- 组件一律参数化 `(id, 位置, 尺寸, 颜色)`，双产线各给实现；
- **验收**：每个组件在 demo 画廊页双产线渲染一致。

### F7 可视化报告（P1）

- `report.md` 升级为单文件 HTML 报告：并排图、diff 热力图、溢出标注、结点 N2–N6 状态灯。

### F8 AI 规格书生成（P2，v2 旗舰）

- 输入原图 + 视觉模型 → 输出 spec 草稿；人工只需核对文案与微调坐标（即结点 N1 的人机分工）；
- 生成结果必须通过 F1 校验器后才允许 build；
- **验收**：对标准测试图集，spec 草稿人工修改量 < 30%。

### F9 Web UI（P2）

- 上传 spec/原图 → 在线预览双产物 → 下载；复用同一引擎核心，不做第二套渲染逻辑。

### F10 批量与 CI（P2）

- `snap2edit check` 退出码语义化（0/2），提供 GitHub Actions 示例 workflow；
- 目录级批量 build/check。

## 6. 关键设计决策

| 编号 | 决策 | 理由 |
|---|---|---|
| D1 | **规格书驱动**而非端到端像素转换 | 流程中唯一不可确定性自动化的环节是"看图写规格"（N1）；把它留给人/LLM，其余全部工具化，v0 即可 100% 可靠 |
| D2 | **同一元素树渲染两遍** | 从根上消除 P1（双产物漂移）；文案清单进 spec，门1/门2 共用 |
| D3 | **v1 形态为 CLI** 而非 Web 应用 | 流程含人工视觉结点（N3/N5 的"像不像"最终由人裁决）；CLI 易嵌入 CI 与 Agent 流水线；Web UI 留 v2 |
| D4 | **YAML** 而非 JSON | 手写友好、支持注释，适合人机共编 |
| D5 | **依赖最小集**：python-pptx / Pillow / numpy / PyYAML，playwright 仅为可选 extras | 降低安装门槛；截图门缺失时优雅降级而非失败 |
| D6 | **PPTX 默认字体 Microsoft YaHei、HTML 侧 Noto Sans SC** | 交付物在 Windows/PowerPoint 环境开箱即用；浏览器侧用开源字体保证渲染一致 |

## 7. 非功能需求

| 维度 | 要求 |
|---|---|
| 兼容性 | PPTX 兼容 PowerPoint 2016+ / WPS / Keynote 导入；HTML 兼容 Chrome/Edge/Safari |
| 性能 | 200 元素级 spec：build < 5s，check（含截图）< 15s |
| 可移植 | 纯 Python + 可选系统工具（LibreOffice/poppler 仅高级校验需要）；字体缺失时按字符宽度估算量宽 |
| 可扩展 | 新元素类型 = svgout + pptxout 各加一个分支 + verify 可选校验，不改框架 |
| 错误体验 | spec 错误必须含元素定位与修复建议；校验失败给出"改哪里"而不是"不对" |
| 安全 | 不上传用户文件；AI 功能（v2）默认本地文案先行、图片调用显式 opt-in |

## 8. 技术方案概要

### 8.1 架构

```
spec.yaml ─▶ spec.validate ─┬─▶ svgout ──▶ <name>.html   ─┐
                            └─▶ pptxout ─▶ <name>.pptx   ─┤
                                                          ├─▶ verify.run_checks
原图(可选) ───────────────────────────────────────────────┘        └▶ report.md / 退出码
```

### 8.2 核心公式（已内置 geometry.py）

```text
EMU/px = 幻灯片宽 EMU ÷ 画布 px 宽        # 16:9(12192000×6858000) + 1280×720 → 9525
pt/px  = (幻灯片高 EMU ÷ 914400 × 72) ÷ 画布 px 高   # 同上 → 0.75
字宽实测 = ImageFont(size=100).getlength(t) / 100 × size
```

### 8.3 依赖

| 依赖 | 用途 | 必需 |
|---|---|---|
| python-pptx | 产线② 原生形状/文本框/连接线 | ✅ |
| Pillow | 量宽、截图分析 | ✅ |
| numpy | 块差异矩阵、非空白率 | ✅ |
| PyYAML | 规格书解析 | ✅ |
| playwright | 门4 截图（浏览器内核） | 可选 |
| LibreOffice / poppler-utils | PPTX 渲染校验（CI 扩展） | 可选 |

## 10. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| PIL 量宽与 PowerPoint 实际渲染存在字体级差异 | 中 | 门3 预留 5% 余量；文档声明字体映射表；必要时按字体配置度量文件 |
| LibreOffice 与 PowerPoint 渲染差异导致"校验像≠打开像" | 中 | 门3 数值校验兜底；CI 中以 soffice 渲染为参考而非绝对标准 |
| SVG/PPTX 文本基线机制不同带来的 ±2px 错位 | 低 | 已在两产线统一"y=文本块顶部"语义；组件级微调字段留白 |
| AI 生成的 spec 质量不稳（v2） | 中 | 生成结果必须过 F1 校验器 + 人工确认 N1 后才允许 build |
| 同名/同域项目混淆 | 低 | 已完成 PyPI 与 GitHub 查重；命名记录于 README |

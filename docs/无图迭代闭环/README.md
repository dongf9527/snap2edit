# 007 · 无图迭代闭环 —— texts 缺项 → 门1/门2 拦截 → 纯报告自动修正

> 案例编号 007 · 2026-11-03 · 在线管线 `/api/refine` **无图模式**实测
> 前作：[refine自动回询闭环](../refine自动回询闭环/)（006，**附原图**视觉比对修正）

## 案例定位

006 验证的是「附原图」的 refine 闭环（失败项 + 视觉模型看图比对）。
本案例验证 **007：不传原图**的 refine 闭环 —— 对应 studio 可视化编辑器的直通场景：
用户在编辑器里手工维护 spec，没有"源图片"可附，校验未通过时把**报告失败项纯文本回询**视觉模型修正。

这是 `/api/refine` 入参放宽（`image`/`meta` 改为可选）之后的第一个完整实测案例。

## 实验设置

| 项 | 值 |
|---|---|
| 入口 | `POST /api/refine`（studio 构建卡片「构建并自动迭代」同款请求） |
| 初始 spec | `spec_v1_含缺陷.yaml`（3 元素小型图，texts 清单 2 条） |
| 缺陷注入 | texts 清单追加一条渲染中**不存在**的文案：「这条文案在渲染中不存在，必须新增一个text元素」 |
| 模式 | **无原图**（不传 `image`/`meta`，VLM 仅按报告失败项修正） |
| 迭代轮次 | maxRounds=2（实际 1 轮修正即通过） |
| 总耗时 | **9.4s**（2 次构建 + 1 次 VLM 修正；006 附图模式同流程为 43.9s） |

## 过程时间线（摘要，全文见 `事件时间线.txt`）

```
第1次构建（spec_v1_含缺陷.yaml）
    ↓ ✗ 2 项未通过：
      门1 交付物① HTML 文案清单全部在场（缺失: '这条文案在渲染中不存在…'）
      门2 交付物② PPTX 文本框文案清单全部在场（同上）
    ↓ failures 纯文本回询 VLM（系统提示 + 当前 spec JSON + 修正指令，无图片）
第1轮修正完成（spec_v2_修正后.yaml）
    ↓ VLM 修法：新增 e4 text 元素（x:48, y:180, size:20）承接缺失文案，texts 三条一一对应
第2次构建（spec_v2_修正后.yaml）
    ↓ ✓ 四道门全部通过 → PPTX→PDF → done(ok=true, rounds=1)
```

## 关键结论

1. **双产线同步拦截**：texts 清单缺项同时被门1（HTML `<text>` 清单）与门2（PPTX 文本框清单）捕获，
   报告 failures 把缺失文案原文反馈给模型——模型据此**新增 text 元素**而非简单删清单条目，
   与 006 的修法一致，说明无图模式下修正提示词足以引导正确修法。
2. **无图模式成本极低**：无需上传/传输图片，VLM 上下文只有 spec JSON + 错误清单，
   全程 9.4s（对比附图模式 43.9s），适合编辑器内高频迭代。
3. **适用边界**：无图模式只能修「结构/清单/边界」类错误；涉及"画得像不像原图"的视觉偏差
   仍需附原图（006 场景）。
